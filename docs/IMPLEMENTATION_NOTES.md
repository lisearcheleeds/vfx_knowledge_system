# 実装上の補足

2026-10-04のユーザー申し送りを、[設計書](../vfx_knowledge_system_design.md)に対する実装上の前提として記録する。

## 1. 探索と採用を区別する

`candidate`、`alternative`、`enhances`、`implemented_by` のリンク先をすべて必須構成として取り込まない。候補を比較・選択した後に、採用した構成の必須依存を解決する。すべてのエンジン用Adapterを同時に要求しない。

索引・逆参照・検索・`related` は探索用。`dependencies` は明示的な採用ノードを起点に、`requires` と `composes: required` だけを処理する。評価先や意味のリンクも自動採用しない。

## 2. 自然言語の条件を自動判定しない

初期仕様の `when` はAI・人間が読む判断材料である。構造検証成功は適用条件・性能条件を満たした証拠ではない。

条件付き必須依存は、適用判断と理由がない場合に未判定として返す。判断を渡した場合も、ツールが条件の成立を検証したとは扱わない。将来自動判定を追加する場合は、対応できる条件と判定不能な条件を分ける。

## 3. 知識追加でプログラム変更を必須にしない

既存スキーマ内のSemantic、Recipe、Techniqueと関係の追加は、Markdownの追加・更新と索引再生成で対応する。検索・検証プログラムへエフェクト名ごとの分岐をハードコードしない。

管理語彙のタグ追加は `schemas/graph-config.json` で行える。ノード種別・関係規約・メタデータ構造の変更は、通常の知識追加とは分けたスキーマ変更として扱う。

## 4. 説明用の例と登録知識を区別する

設計書のYAML例は、未作成の参照先と説明用の数値を含む。実際のノードへ登録する場合は参照先を整備する。

登録対象は `knowledge/`、`adapters/`、`evidence/` のMarkdownのみ。設計書・テンプレート・テスト用データは知識として登録しない。未作成の概念は[追加候補](OPEN_ITEMS.md)へ記録し、空のノードを大量に作らない。

## 5. 文書の存在だけで検証済みにしない

エンジンで実行していないRecipe・Adapterは、その事実を明示する。出典から確認できた仕様、設計上の仮説、実際の再現結果を分ける。実測値・成功記録を補完または創作しない。

初期版は全ノード `draft`。火球の品質基準版・Core削減版と斬撃残像の実行Evidence 3件を `reviewed` とし、Recipe・Technique・Adapterは `draft` を維持している。`validated` の形式検証では対象IDを明記した根拠を要求し、Recipe・Adapterにはエンジン実行記録を要求する。形式を通すために架空の記録を埋めない。証拠の真正性と適用範囲はレビューする。

## 6. 再利用・拡張と不正入力を確認する

初期確認には、次を含める。

- 複数のRecipeが同じTechniqueを共有する。
- 一つの役割に複数の候補がある。
- 新しいノードを追加すると索引・逆参照へ反映される。
- 重複ID、存在しない参照先、必須依存の循環を検出する。

この確認は知識基盤の構造確認であり、VFX制作の成功記録ではない。

## 7. 二つの完成条件を分けて報告する

文書、スキーマ、索引、構造検証が揃った段階を知識基盤の完成として扱う。AIがエンジンで制作・撮影・評価・修正し、結果から知識更新まで実行できた段階を制作ワークフローの実証とする。

実行環境がない部分には、未検証事項と次の検証手順を残す。[現在の状態](STATUS.md)でそれぞれの到達点を記録する。

## 8. 最高品質基準版の制作工程（2026-10-06確定）

[WORKFLOW](../WORKFLOW.md)と[Aの工程表](QUALITY_BASELINE_WORKFLOW.md)を制作の正本とする。コストを度外視し、完成像・全体の時間演出・役割の因数分解を先に定める。既存Recipe/素材や機械確認を全体の美術判断へ置き換えない。

Profileや旧設計の性能・制作時間・反復回数・初稿数値をAの品質上限へ適用しない。ゲーム用アセット化は完成承認後の[B](GAME_ASSET_WORKFLOW.md)へ分離し、完成実物を再因数分解する。工程表の作成と実際の品質達成を別に報告する。
